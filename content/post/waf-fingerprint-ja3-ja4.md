CloudflareのWAFのログを眺めていると、`JA3Hash`や`JA4`といったフィールドが目に入ることがあります。  
値は`b4da7...`や`t13d1...`のような、意味の分からない文字列です。

これは「フィンガープリント(指紋)」と呼ばれる情報です。名前だけ聞くと「アクセスしてきた人を個人として特定するもの」に聞こえますが、実際にわかることはもう少し違います。  
この記事では、フィンガープリントが何を元に作られていて、ログから何が読み取れるのかを整理します。

## フィンガープリントの正体：TLS接続の「癖」を数値化したもの

WAFログでいうフィンガープリントは、多くの場合「JA3」または「JA4」と呼ばれる方式で作られた指紋のことです。これはHTTPリクエストの中身（URLやCookie、User-Agentヘッダーなど）を見ているのではなく、**HTTPS通信が始まる直前のTLSハンドシェイクの構造**から作られています。

ブラウザやプログラムがHTTPS接続を始めるとき、最初に送る「Client Hello」というパケットには、次のような情報が含まれます。

- 対応しているTLSのバージョン
- 使える暗号方式(cipher suites)の一覧とその並び順
- 拡張機能(extensions)の種類と並び順
- 対応している楕円曲線の一覧

これらの項目の組み合わせと並び順は、通信ソフトが使っているTLSライブラリによって決まっており、同じソフト・同じバージョンであればほぼ同じパターンになります。JA3/JA4は、このパターンをハッシュ化して短い文字列に変換したものです。

> **JA3/JA4**: TLS Client Helloの構造(暗号方式や拡張の並び順など)からハッシュ化して作られる、通信ソフトの特徴を表す識別子。JA4はJA3の後継で、より詳細な情報を反映する。

## Cloudflareのログに実際に出てくるフィールド

Cloudflareのログ(Logpushで出力されるHTTPリクエストログなど)には、次のようなフィールドが含まれます。

```json
{
  "JA3Hash": "b4da7...",
  "JA4": "t13d1...",
  "JA4Signals": {},
  "BotScore": 1,
  "BotScoreSrc": "Machine Learning",
  ...
}
```

- **JA3Hash**: 従来方式のTLSフィンガープリント(MD5ハッシュ)
- **JA4**: JA3の後継となる新しい方式のフィンガープリント
- **JA4Signals**: 同じJA4フィンガープリントを持つ直近1時間分のグローバルなトラフィックを集計した、追加のコンテキスト情報

なお、これらはLogpushで出力される際の内部的なフィールド名です。Cloudflareダッシュボードの画面上では、それぞれ次のような表示名になっています。

| Logpushフィールド名 | ダッシュボード表示名 |
| --- | --- |
| JA3Hash | JA3 フィンガープリント |
| JA4 | JA4 フィンガープリント |
| JA4Signals | JA4 インターリクエスト信号 |

同じものを指しているので、ダッシュボードで見る場合とログを直接見る場合で名前の見え方が変わる、と捉えておくと混乱しません。

`JA4Signals`(ダッシュボードでの「JA4 インターリクエスト信号」)の中身は、単純な「良い/悪い」の判定ではなく、次のような比率・順位・分位数のデータです。

```json
{
  "h2h3_ratio_1h": 0.988,
  "browser_ratio_1h": 0.936,
  "heuristic_ratio_1h": 0.00007,
  "cache_ratio_1h": 0.189,
  "reqs_rank_1h": 850,
  "uas_rank_1h": 901
}
```

たとえば`browser_ratio_1h`は「この指紋を持つ直近1時間のトラフィックのうち、ブラウザらしいふるまいをしている割合」を示します。この値が極端に低ければ、その指紋は主にツールやスクリプトから使われている可能性が高い、と判断する材料になります。

これらは単体のフィールドとしてログに残るだけでなく、`BotScore`の算出にも使われています。

> **注意**: JA3/JA4フィンガープリントとJA4Signalsは、Bot Managementを購入したEnterpriseプランの顧客のみが利用できる機能です。Free/Proプランのログにはこれらのフィールドは出てきません。

## フィンガープリントから何がわかるのか

### 1. どんな種類の通信ソフトを使っているかの傾向

JA3/JA4の値ごとに、「これはChromeブラウザの典型的なパターン」「これはPythonの`requests`ライブラリの典型的なパターン」「これは特定のボットフレームワークのパターン」といった傾向が知られています。値そのものから直接ソフト名がわかるわけではありませんが、既知のパターンと照合することで、大まかな種類を推測できます。

### 2. User-Agentとの「矛盾」を見つけられる

これがフィンガープリントの一番実用的な使い方です。

User-Agentヘッダーは、リクエストを送る側が自由に書き込める文字列です。「Chromeです」と自己申告することは、攻撃者やボットにとって簡単にできてしまいます。

一方、TLSハンドシェイクの構造は、実際に使っているTLSライブラリの実装に依存するため、書き換えるにはそのライブラリ自体を改造する必要があり、User-Agentを書き換えるよりもずっと手間がかかります。

そのため、「User-Agentは最新のChromeを名乗っているが、JA4のパターンは特定のスクレイピングツールのものと一致している」といったギャップから、なりすましボットを見つけ出せます。

### 3. IPやUser-Agentを変えても、同じ「道具」を使い続けている限り追跡できる

分散的な攻撃(複数のIPアドレスから少しずつリクエストを送る、User-Agentを毎回変えるなど)を行うボットでも、使っているツールやライブラリそのものを変えない限り、JA3/JA4の値は同じままです。これにより、見た目は別々のリクエストに見えても、実は同じ道具から送られたものだと束ねて識別できます。

## 過信できない部分:限界と注意点

フィンガープリントは強力な補助情報ですが、単体で「これは悪い通信だ」と断定できるものではありません。

- **同じ指紋を共有する無関係なクライアントが存在する**: 同じTLSライブラリ・同じバージョンを使っている正規のユーザーとボットが、たまたま同じJA3/JA4値になることがあります。
- **指紋を分散させる手法がある**: TLSのパラメータをランダム化して、リクエストごとに異なる指紋を生成する手法(JA3 randomizationなど)も存在します。JA4はこうした回避策への対策として、より細かい情報を扱えるように設計されています。
- **単独ではなく組み合わせで使われる**: Cloudflareも、JA3/JA4だけでBot Scoreを決めているわけではありません。機械学習モデルや振る舞い分析、既知の悪性パターンとの照合など、他の検出エンジンと組み合わせた結果として最終的なスコアが算出されます。

## まとめ

- WAFログの「フィンガープリント」は、多くの場合JA3/JA4と呼ばれるTLSハンドシェイクの指紋のこと
- HTTPリクエストの内容ではなく、通信ソフトのTLS実装の「癖」を数値化したもの
- User-Agentのような自己申告情報と違い、簡単には書き換えられないため、なりすましの矛盾を見つける材料になる
- IPやUser-Agentのローテーションを跨いで、同じ道具からのリクエストを束ねて識別できる
- ただし単独では個体識別も悪性判定もできず、他の検出手法と組み合わせて使うのが前提

Cloudflareのログにこれらのフィールドが出てきたときは、「何かを個人として特定している」わけではなく、「どんな通信ソフトの癖を持つリクエストなのか」を示している、と捉えると理解しやすくなります。
